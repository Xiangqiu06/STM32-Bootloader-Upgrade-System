# 项目难点：串口接收导致 DATA 应答迟到 2.4 秒

> 《STM32 固件升级系统》调试中遇到的最曲折的一个问题，完整记录：背景 → 现象 → 排查 → 根因 → 解决。最终方案落在 `platform/bsp_uart_dma.c`，原理详见主文档 6.1 节。

## 一、问题出现的背景

升级用的是**停等协议**：上位机发一包 DATA（最大 1039 字节），等设备回一个 ACK，收到才发下一包；**超过 2000ms 没等到 ACK 就重发并重新握手**。

设备端（STM32F103）的接收链路当时是这样设计的：

```
CH340 → USART1 → DMA 循环写入 s_dma_buf[2048]（硬件自动搬运，不占 CPU）
                        ↓
        帧结束中断（IDLE）：总线静默时触发，把新数据搬进环形缓冲
                        ↓
        主循环从环形缓冲取字节 → 协议解析器 → 写 W25Q64 → 回 ACK
```

选"帧结束中断"做搬运触发，是因为帧长不固定（DATA 1039 字节、ACK 只有 11 字节），没法靠字节计数判断"一帧收完了"；而"总线静默 1 个字节时间"是天然的帧边界信号。这个方案让 CPU 全程零参与收字节，教科书标准写法——**问题恰恰出在把它当成了唯一通道**。

## 二、现象

START 握手正常（19 字节小帧），但进入 DATA 阶段后**每一包都超时**。日志里有几个很反常的细节：

1. DATA 的 ACK **确实回来了，只是迟到约 2.4 秒**——超过 2000ms 超时线，所以每包都判定失败；
2. ACK 的到达时刻，**永远是"下一次重发的 START 到达之后"再过 7ms**；
3. 设备端"正在收包"的进度打印（`[UP] progress`）和 ACK **同一毫秒**打出——说明数据不是收得慢，而是**收到后一直没人处理，直到下一帧到来才被一起处理**；
4. 小帧（START）的 ACK 每次都正常，**只有大帧（DATA）出问题**。

## 三、如何分析排查

按时间顺序排除，每一步都是靠"原始收发日志 + 时间戳"推进的：

1. **怀疑上位机没发出去** → 抓串口原始 RX 日志，ACK 字节确实到了，逐字节验算 CRC 也对 → 排除；
2. **怀疑设备端 Flash 写太慢** → 量 W25Q64 写 1KB 约 10ms，和 2.4 秒差两个数量级 → 排除；
3. **盯着时间戳找规律（突破口）**：ACK 到达 = 下一帧 START 到达 + 7ms，稳定复现。这说明上一帧 DATA **早就到了设备，只是滞留在某处**，直到下一帧把它"带活"——问题不在处理速度，在**搬运触发**；
4. **锁定接收链路**：字节由 DMA 硬件写入，唯一可能的滞留点是"DMA 缓冲 → 环形缓冲"这一步，而它的触发条件是帧结束中断。回头查证：**大帧结束后这个中断没有触发**（小帧每次都正常）；
5. **交叉验证**：用 Python 模拟设备端状态机，复现了"半帧滞留、下一帧带活"的全部现象，确认协议状态机没问题，是接收侧的问题。

## 四、根因

帧结束中断的触发条件是 **UART 检测到总线静默 1 个字节时间**（约 87µs）。但 USB 转串口芯片（CH340）向 MCU 交付字节是**分批的、批间间隙抖动**的——一帧 1039 字节分几批到达，若最后一批之后恰好凑不出足够的静默间隙，中断就永远不来。

一句话：**整个方案把"数据一定会被处理"押在了一个可能不发生的硬件事件上**。事件没发生没有任何报错，数据就静静躺在 DMA 缓冲里，直到下一帧的到来"顺便"把它冲进解析器。

## 五、怎么解决的

彻底放弃"中断通知"，改成**主循环轮询**——不再等待事件，而是主动查状态：

```c
/* 主循环每圈调用一次（一圈几十 µs） */
void bsp_uart_poll(void)
{
    /* 1. 读 DMA 剩余计数 CNDTR，反推 DMA 当前写指针位置 */
    pos = UART_RX_DMA_SIZE - __HAL_DMA_GET_COUNTER(huart->hdmarx);

    /* 2. 与上次位置 s_last_pos 之间的新数据搬进环形缓冲 */
    if (pos == s_last_pos) return;          /* 没有新数据，直接走 */
    if (pos > s_last_pos) {
        ring_push(&s_dma_buf[s_last_pos], pos - s_last_pos);       /* 正常推进 */
    } else {
        ring_push(&s_dma_buf[s_last_pos], UART_RX_DMA_SIZE - s_last_pos); /* 回卷收尾 */
        ring_push(&s_dma_buf[0], pos);                                 /* 从头再收 */
    }
    s_last_pos = pos;
}
```

主循环里一行 `bsp_uart_poll();`，删掉中断函数和相关的中断使能，代码反而变短了。

**效果**：DATA 的 ACK 从 2.4 秒变成毫秒级，19904 字节升级包一次传输成功，整个升级闭环跑通。

## 六、教训

- **中断是"事件通知"，快但可能漏；轮询是"状态查询"，慢不了多少但必然执行。** 当方案的正确性押在"中断一定会来"上，它就不可靠。对确定性要求高的场合，轮询是更好的默认选择；
- **排查"设备没响应"类问题，第一时间看带时间戳的原始收发日志**——"数据什么时候到的"比"数据是什么"更能定位问题；
- **异常数据里的周期性规律直接指向时序根因**。"+7ms""永远和下一帧一起出现"这两条规律，比任何假设都值钱。
